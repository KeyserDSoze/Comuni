# ADR 0070 — Revoca owner-only degli Admin OIDC con ultimo Admin protetto

- Data: 2026-11-16.
- Stato: Accepted per procedura offline e test sintetici; produzione, IdP reale e approvazione legale **non verificati**.
- Issue: #81, sotto #2/#3/#4/#5/#10; estende ADR 0021, 0022, 0025, 0038 e 0069.
- Riferimenti: [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [OIDC Core §5.7: issuer+subject](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStabilityAndUniqueness).

## Problema e confine di sicurezza

Il bootstrap del primo Admin (#31) e l'enrollment di un secondo Admin (#80) sono operazioni owner-only. Mancava una procedura per **disabilitare** un Admin dimesso o compromesso senza cancellare l'audit né lasciar privo di amministratori il Comune. L'API comunale permette già soltanto Reader/Officer (guard server e RLS); estenderla direttamente al ruolo Admin senza un percorso di approval verificato allargherebbe i privilegi. Un JWT OIDC valido continua a esserlo fino alla propria scadenza, ma la **membership database** deve cessare di autorizzare immediatamente ogni nuova richiesta.

## Decisione

1. Introdurre unicamente `scripts/postgres/revoke-admin.sql`, chiamabile **offline dal proprietario dello schema** PostgreSQL, su runner privato con TLS, senza endpoint API o nuova applicazione. Nessun SQL runtime, API tenant, token Superadmin o ruolo claim può revocare direttamente un Admin. Non usare `SECURITY DEFINER`, modifiche RLS o grant.
2. Input trasmessi **solo tramite environment**, mai argv/log: `COMUNI_REVOKE_ADMIN_ORGANIZATION_ID` (UUID), `COMUNI_REVOKE_ADMIN_IDENTITY_ISSUER` (HTTPS issuer OIDC esatto), `COMUNI_REVOKE_ADMIN_SUBJECT` (identità case-sensitive), `COMUNI_REVOKE_ADMIN_CHANGE_TICKET`, `COMUNI_REVOKE_ADMIN_APPROVER`, `COMUNI_REVOKE_ADMIN_REASON_CODE`. Il reason è un codice conservativo, non dati sanitari, testo libero o motivazioni contenenti PII. Un secondo reviewer autentica **esternamente** identity, mandato, ticket, MFA, titolarità del Comune, piano di recupero e indipendenza approvatore/operatore: il controllo di formato non costituisce autentica approvazione.
3. Transazione PostgreSQL unica: controllare `current_user` contro i proprietari di organizations/memberships/audit, validare tutti gli input, acquisire `SELECT ... FOR UPDATE` sulla organization e negare quelle `created`, `suspended` o assenti. La membership da revocare deve essere **Admin, issuer+sub esatti, attiva** e l'operazione è permessa solo se resta **almeno un altro Admin attivo con issuer OIDC HTTPS di formato approvato**. Il lock per organization serializza contemporaneamente due revoche differenti, evitando che entrambe contino l'altra come superstite. Nessuna cancellazione di righe e nessuna mutazione dei moduli.
4. Modifica `is_active=FALSE` per la sola riga Admin del Comune selezionato; registrare **nella stessa transazione** l'evento append-only `platform.membership.admin.revoked`, `resourceType=platform.membership`, `resourceId=md5(org|Admin|sub|issuer)::uuid` (pseudonimo, non anonimo), `actor=db-owner:<login>` e `correlationId=admin-revoke:<ticket>`. Il codice motivo e il revisore restano **nel sistema di change esterno**, non in audit per minimizzazione. Non salvare email, subject/issuer in chiaro, OIDC token o secret in audit.
5. Retry con **identici issuer+sub e ticket**: se il target è già inattivo e esiste **esattamente un evento** di revoca per resource+ticket, il risultato è no-op. Un ticket usato per altro target, un ticket differente per membership già revocata, issuer diverso, ruolo diverso, soggetto inesistente, Admin legacy o revoca incompleta vengono rifiutati senza mutazioni. Il percorso non riattiva né scambia ruoli.
6. Il runtime continua a risolvere ogni autorizzazione da membership PostgreSQL server-side sotto RLS firmata. Un JWT RS256 **già firmato** non acquisisce eccezioni: alla nuova richiesta API `/context` e `/admin/*` di chi è stato revocato si ottiene 403, mentre altri Admin/Comuni rimangono autorizzati. Non si promette interruzione delle richieste **già in corso**, revoca del token presso l'IdP, refresh token o sessioni di altre applicazioni.
7. TDD test-first con xUnit, PostgreSQL 17, psql e fixture OIDC locale RS256; copre blocco ultimo Admin, serializzazione concurrente, retry, errori issuer/ticket/input, isolamento cross-tenant, owner-only e risposta immediata 403 con token invariato. Playwright e tutta la suite CI 7/7 rimangono regression gate, nessun frontend nuovo.

## Operatività ed emergency handling

**Procedura autorizzata:** verificare prima due Admin attivi e validi per il Comune, acquisire change a quattro occhi con identity proof e reason code, valutare accesso di recupero e backup. Da un runner privato autorizzato con schema owner, fornire environment tramite canale segreto e avviare `psql -X -q -v ON_ERROR_STOP=1 -f scripts/postgres/revoke-admin.sql` senza `psql -a/-e`, `set -x` o logging di parametri. Verificare separatamente 1 solo audit di revoca e lo stato delle membership; non leggere/stampare credenziali o dati personali nei ticket GitHub.

Per un **compromesso dell'unico Admin**, la procedura rifiuta la revoca; è necessario un piano di emergenza esterno: sospendere l'organization con l'attuale procedura owner-only (che nega subito nuove richieste), coordinare revoca IdP/token e nuovo Admin verificato con due operatori, poi riesaminare i criteri di riattivazione. Non bypassare il controllo ultimo Admin né abilitare automaticamente servizi. L'attuale enrollment #80 rifiuta un roster che contiene Admin inattivi; l'eventuale sostituzione post-revoca richiede un successivo processo di recovery esplicitamente progettato e non deve essere forzata tramite SQL runtime.

Niente produzione reale, nuove credenziali, permessi Azure, Terraform apply o modifica dell'IdP in questa slice. La copertura audit generale, attuazione procedura a quattro occhi, monitoring/retention e controllo legale rimangono nelle #2/#3/#4/#5/#10.

## Emendamento al trasporto input (#96, ADR 0080)

La descrizione storica del trasporto con psql quoted literals riflette l'implementazione originale. L'attuale revoke-admin.sql usa un canale client-side \copy a tabella temporanea con allowlist dei sei COMUNI_REVOKE_ADMIN_* e non inserisce issuer/sub nel testo delle statement SQL. La policy di revoca qui definita (owner, organizzazione operativa, ultimo Admin, lock, audit, retry e concorrenza) è invariata. Le verifiche su IdP reale, payload COPY, pgAudit Azure e pipeline SIEM restano aperte in #84/#86/#92.
