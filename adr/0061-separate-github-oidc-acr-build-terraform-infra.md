# ADR 0061 — Separazione OIDC del rilascio: infra preflight → build ACR → infra Terraform

- **Data:** 2026-11-16.
- **Stato:** Accepted per contratto software e CI offline; provisioning Entra/FIC e prova Azure **NON eseguiti**.
- **Issue:** #71 (slice della #70, parent #65/#6), dopo ADR 0059/0060.
- **Fonti:** [Microsoft — autenticare Azure da GitHub Actions con OIDC](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure); [Azure/login](https://github.com/Azure/login); [Microsoft — RBAC ACR e ABAC](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-abac-repository-permissions); [Microsoft — Azure CLI account clear](https://learn.microsoft.com/en-us/cli/azure/authenticate-azure-cli-interactively); [GitHub — OIDC per Azure](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-azure).

## Contesto e minaccia

La #69 verifica il principal registrato che dispone di `AcrPush`, distinto dalla UAI della Container App (`AcrPull`), e nega Contributor/Owner ereditati. Il workflow preesistente usava però **lo stesso `AZURE_CLIENT_ID`** per build/push/lock e per Terraform state/Key Vault/apply. Il principal di Terraform può necessitare autorizzazioni di control-plane ampie, incompatibili con il principio di minimo privilegio del builder. Un registro ACR passato inconsapevolmente da `rbac` a `rbac-abac` interromperebbe i ruoli legacy.

La separazione è distinta sia dall'identità runtime dell'app sia dalla provenienza firmata dell'immagine. Senza un guard del **contesto Azure CLI attivo**, due chiamate `azure/login` nello stesso runner non costituiscono prova che un comando di Terraform non usi ancora il principal di build o viceversa. Il workflow manuale deve operare solo dalla HEAD `refs/heads/main` e dal repository `KeyserDSoze/Comuni`.

## Decisione

1. **Due Microsoft Entra service principals con credenziali federate GitHub separate, predisposte esternamente dall'owner:**
   - `AZURE_CLIENT_ID` (secret GitHub Environment `production`): principal infrastruttura. Autorizzazioni Azure Resource Manager, Terraform state, Key Vault e lettura RBAC da approvare separatamente. Non viene usato nel push del container.
   - `AZURE_ACR_PUSH_CLIENT_ID` (nuovo secret Environment `production`): principal **build/registry**. `AcrPush` diretto all'ACR (e letture/lock tag/manifest effettive da verificare); **nessun ruolo Owner/Contributor** ereditato; differente da `AZURE_CLIENT_ID` e dalla UAI ACA.
   - La UAI `<prefix>-app-identity` creata da Terraform conserva il ruolo `AcrPull` legacy e nessuna credenziale federata GitHub. Il registry resta `rbac` e `admin_enabled=false` senza modifiche Terraform.
   - Per ciascun service principal, FIC da creare/approvare con **issuer** `https://token.actions.githubusercontent.com`, **audience** `api://AzureADTokenExchange`, **subject** `repo:KeyserDSoze/Comuni:environment:production`. Proteggere GitHub Environment con reviewer e restrizione a `main`. Il workflow rifiuta `GITHUB_REPOSITORY`, `GITHUB_REF` e `GITHUB_EVENT_NAME` non approvati **prima di ogni login**; non utilizzare input del dispatch come client-ID o credenziali.
2. **Handoff in tre fasi nello stesso job su runner GitHub-hosted, tutte fail-closed:**
   1. `azure/login@v2` con `AZURE_CLIENT_ID`; `check-azure-oidc-session.py` verifica clientId attivo e tenant/subscription della CLI. Il preflight read-only `check-acr-role-boundary.py` (richiede privilegi di lettura dei role assignment) riceve **entrambi** gli appId e li pretende diversi; verifica UAI pull-only e builder `AcrPush`.
   2. `az logout` e `az account clear` senza log dell'output, poi `azure/login@v2` con `AZURE_ACR_PUSH_CLIENT_ID`; nuovo controllo CLI di `servicePrincipal`, appId, tenant e subscription. **Solo con questa sessione** eseguire `az acr login`, Docker build/push, confronto digest del push con ACR, lock tag+manifest, Trivy, firma SPDX e SLSA e verifica GitHub delle attestazioni.
   3. `docker logout <registry>` **obbligatorio senza fallback**, `az logout`, `az account clear`, poi nuovo `azure/login@v2` con `AZURE_CLIENT_ID` e guard CLI prima di `terraform init`, checks read-only versioni Key Vault, `terraform plan`, security gate e `terraform apply` della candidata al 0%; post-stage resta in sola lettura con la sessione infra.
3. **Confinare i segreti DB alla fase infra.** `TF_VAR_postgres_admin_password` e `TF_VAR_postgres_runtime_password` sono rimossi dall'`env` del job (ereditata da tutti i processi) e iniettati **solo nell'env del passo plan/apply**, mai in Docker/Trivy/build/Sigstore. Manteniamo il plan Terraform confidenziale con `umask 077`, pipe senza print e trap cleanup preesistenti.
4. **Identity guard** `scripts/azure/check-azure-oidc-session.py` legge esclusivamente `az account show --query "{id:id,tenantId:tenantId,user:user}" -o json`, verifica `user.type=servicePrincipal`, `user.name == expected clientId`, `tenantId` e `id` uguali ai UUID del GitHub Environment, e clientId build/infra differenti. Fallisce su output nullo, lista, ambiguo, utente interattivo, SP errato, CLI senza login o risposta oversized. Cattura stdout/stderr Azure e usa solo messaggi statici, senza stampare i valori; i controlli Azure CLI sono read-only.
5. **TDD RED→GREEN** `tests/infra/test_azure_oidc_session_handoff.py` fake `az` e workflow structure checks + `tests/infra/test_aca_acr_rbac_preflight.py` aggiornato per `--infra-client-id`. Condizione di completamento software: tutti i 7 job CI (Python/Terraform, xUnit/PostgreSQL, React/Playwright, CodeQL C#/JS, SCA NuGet/npm, Docker) verdi sul medesimo commit `main`.

## Limiti: non è ancora una segregazione forte

Le tre fasi condividono **lo stesso job/runner**: un codice build compromesso potrebbe interferire con filesystem, processi o richiedere nuovi GitHub OIDC ID token; il logout riduce la permanenza di sessioni CLI e Docker, ma **non è un confine crittografico tra job**. Il job continua ad avere il permesso `id-token: write`. L'isolamento più forte richiede separazione in **due job/runner** con differenti GitHub Environments, digest verificato come output firmato e binding dell'attestazione tra fasi, più una review del modello di trust (parent **#70**). Non dichiarare la #70 conclusa con questo slice.

Il gate `az account show` convalida il principal attivo, **non** l'effettiva autorizzazione, la grafia delle FIC, la provenienza della credenziale del runner o la mancanza di accesso a un token antecedente. Non abbiamo creato service principals, FIC, role assignment, secreti GitHub, non abbiamo eseguito `az login` reale, ACR push/pull/lock né `terraform apply`. Il primo deployment richiede owner approval per entrambe FIC, Microsoft Graph/RBAC, resource scopes, rollback senza downtime, Terraform remote state e test manuali fail-closed. Le #65/#70/#5/#6/#49 restano aperte. La release rimane bloccata se il secret `AZURE_ACR_PUSH_CLIENT_ID` manca o coincide con il principal infrastrutturale.
