# ADR 0056 — Rollout ACA con digest OCI verificato dopo il push e prima di Terraform apply

- Stato: **Accepted per il contratto offline e il workflow**; nessuna validazione con un registry/tenant Azure reale.
- Data: 2026-11-16.
- Issue: #64; sviluppata su `main` dopo ADR 0046, 0053, 0054, 0055.
- Riferimenti ufficiali: [Docker — il push restituisce il digest](https://docs.docker.com/reference/cli/docker/image/pull/), [Azure CLI — az acr manifest show-metadata](https://learn.microsoft.com/en-us/cli/azure/acr/manifest), [ACR — attributi tag e manifest](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-image-lock), [OCI image manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md), [Terraform JSON plan](https://developer.hashicorp.com/terraform/internals/json-format).

## Contesto e trust boundary

ADR 0055 (#63) imponeva `<ACR-managed>/comuni:<GITHUB_SHA>` nella revisione candidata, con suffix `r<SHA12>` e l'unico container consentito. **Un tag è mutabile:** un utente con permesso di push/retag può cambiare il manifest sotto lo stesso nome tra il push del workflow, il preflight del plan e l'uso del registry da parte di Container Apps. La candidata a traffico 0% può essere raggiunta tramite label e ricevere le credenziali SQL/tenant dal Key Vault: un mero controllo del tag non prova che l'immagine avviata sia quella del push autorizzato.

La digest `sha256` identifica il **manifest OCI**, non direttamente il commit Git né una firma di provenienza. La verifica che il manifest recuperato da ACR corrisponda all'output del push del runner riduce la possibilità di distribuire un altro manifest attraverso una mutazione del tag. Non conferisce fiducia in un runner, repository base image o credenziali ACR compromessi.

## Decisione

1. **Raccolta digest indipendente dal plan:** il workflow protetto `.github/workflows/deploy.yml` costruisce `<vars.ACR_LOGIN_SERVER>/comuni:<GITHUB_SHA>` e cattura l'intero stdout di **quel** `docker push` in un file locale temporaneo creato con `mktemp`, `umask 077`, cleanup `trap EXIT`. Il nuovo `scripts/azure/resolve-pushed-image-digest.py` estrae **una sola** riga `<GITHUB_SHA>: digest: sha256:<64hex> size: <numero>`. Il receipt è limitato a 64 KiB, SHA canonico 40-hex lower, registry name 5–50 ASCII lowercase alfanumerico e hostname `<registry>.azurecr.io`. Non derivare l'approvazione dal `TF_VAR_image`, dal piano o dall'elenco arbitrario dei tag.
2. **Confronto reale con il registry:** tramite la credenziale Azure OIDC già stabilita nel job, il tool consulta unicamente `az acr manifest show-metadata --registry <nome> --name comuni:<GITHUB_SHA> --query digest --output tsv --only-show-errors` e richiede lo **stesso identico** `sha256:<64hex>` del receipt. Metadati assenti, output ambiguo, mismatch o comando fallito bloccano la release. Tutto l'output/error di Docker e ACR rimane catturato, mai rilanciato nei log; non leggere i payload Key Vault.
3. **Output autorizzato solo dopo successo:** lo script scrive esclusivamente `TF_VAR_image=<registry>.azurecr.io/comuni@sha256:<digest>` e `CANDIDATE_IMAGE_DIGEST=sha256:<digest>` nel `GITHUB_ENV` del job GitHub. Il primo alimenta `var.image` di Terraform; il secondo è fornito come parametro separato `--candidate-image-digest` al **pre-apply plan gate**, insieme a `--source-commit-sha "$GITHUB_SHA"`. Il gate impone l'esatta URI `<managed_registry>.azurecr.io/comuni@<approved_digest>`. Non accetta tag, digest multipli, host alternativi, repo diversi, init container, valori non canonici o mancanti. La guardia preesistente continua a mantenere stable 100% e candidate 0%, OIDC Production, UAI, Key Vault e PG RLS.
4. **Binding al commit Git intero:** un digest non contiene il commit originario e il suffix `r<SHA12>` ne riporta solo 12 caratteri. Il workflow valorizza ora `TF_VAR_source_commit_sha=$GITHUB_SHA`; il template Terraform espone `Release__SourceCommitSha` come **metadato non segreto** e il gate verifica `value == args.source_commit_sha` e l'assenza di un secret ref. Il valore arriva dal workflow fidato, non da un input HTTP/JWT/tenant. `infra/variables.tf` convalida il SHA e la sintassi digest URI già prima del piano.
5. **Controllo post-apply:** `scripts/azure/verify-staged-revisions.py` accetta come `--expected-image` solo una URI digest `<acr>.azurecr.io/comuni@sha256:<64hex>`, confrontandola con il template ARM dell'unica revisione candidata. Non legge registry credentials né promuove automaticamente il traffico.
6. **TDD RED→GREEN:** prove Python `tests/infra/test_aca_pushed_digest.py` con fake `az`, receipt Docker sintetici e file GITHUB_ENV privati; `test_aca_digest_plan_guard.py` con piani Terraform avversariali; fixture regressione nella suite infra e `test_live_revision_verification.py` con metadati ARM fake. Tutti i job CI 7/7 sul medesimo SHA `main` sono necessari per chiudere #64.

## Esclusioni, rischi residui e processo owner

- Il tag `comuni:<SHA>` può essere **ritaggato dopo** il confronto: l'URI digest già scelta non cambia, quindi l'ACA avvia lo stesso manifest (o fallisce se è stato cancellato); il tag non viene nuovamente risolto in fase di apply. Mutazioni/delete del manifest e cambi IAM possono causare un problema di disponibilità, che richiede monitoraggio e rollback approvato.
- **Non costituisce attestazione firmata della provenienza/SLSA**: un runner compromesso potrebbe costruire e pushare layer malevoli e ottenere digest coerenti; la verifica non valida SBOM, firma Cosign/Notary, digest dei base layer, vulnerability scan o identity RBAC. Prima della produzione progettare policy di immutabilità/retag, least privilege `AcrPush` vs `AcrPull`, provenienza firmata e controllo delle dipendenze container con una issue distinta. Il comando `az acr manifest` è documentato in **preview** e il comportamento va verificato nel reale runner/ACR autorizzato, senza rilassare i controlli se manca.
- Il plan Terraform è confidenziale e resta passato solo in pipe al gate; il binary plan viene rimosso con trap. Questo incremento non esegue `terraform apply`, non autentica un IdP reale, non verifica Key Vault o rete/CA PostgreSQL, non completa lo switch delle secret legacy e non dimostra il rollback in Azure. Le #2/#5/#6/#49 restano aperte.
