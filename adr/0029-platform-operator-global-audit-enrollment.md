# ADR 0029 — Enrollment/revoca owner-only degli operatori piattaforma e audit globale append-only

- Stato: Accepted **solo come procedura offline controllata** (#35), non gestione real-time Superadmin.
- Data: 2026-11-15
- Dipendenze: ADR 0005, 0006, 0008, 0011–0013, 0022, 0025–0028; issue #2/#3/#4/#5/#10/#34/#35.
- Riferimenti: [OIDC issuer + subject](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStabilityAndUniqueness), [PostgreSQL advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html), [psql variables](https://www.postgresql.org/docs/17/app-psql.html#APP-PSQL-INTERPOLATION).

## Gap

L'ADR 0028 separa `platform.platform_operators` dalle membership del Comune, senza seed e senza scritture runtime. Mancava una procedura che permettesse a un operatore **DB owner**, dopo verifica e approvazione indipendenti, di registrare la prima identità `iss+sub`, revocarla e registrare la decisione. L'audit esistente `platform.audit_events` contiene una FK obbligatoria `organization_id`: usare un Comune fittizio per operazioni globali falsificherebbe il confine tenant.

## Decisione

1. La migration EF `202611150011_PlatformOperatorGlobalAudit` aggiunge `operator_id uuid NOT NULL DEFAULT gen_random_uuid()` con vincolo UNIQUE alle identità platform già esistenti, mantenendo `(identity_issuer,subject)` come PK: nessuna abilitazione o rebind automatici. L'ID **casuale e stabile** è un riferimento opaco nei log, anziché memorizzare issuer, subject o un hash soggetto a attacco dizionario. Crea `platform.platform_operator_audit_events` **senza organization_id**, con ID evento UUID, owner actor, action, resource type, resource ID, correlation ticket e data. Trigger BEFORE UPDATE/DELETE/TRUNCATE riusano `platform.reject_audit_change()` (ADR 0006): append-only per DML ordinario, NON tamper-evident contro DB owner/superuser. La migration DOWN viene rifiutata esplicitamente per non cancellare accidentalmente la storia.
2. La procedura `scripts/postgres/manage-platform-operator.sql` viene eseguita tramite `psql -X -q -v ON_ERROR_STOP=1` **solo con l'account proprietario di entrambe le tabelle**. Input obbligatori da un runner autorizzato: `COMUNI_PLATFORM_OPERATOR_IDENTITY_ISSUER`, `COMUNI_PLATFORM_OPERATOR_SUBJECT`, `COMUNI_PLATFORM_OPERATOR_ACTION` (esattamente `enroll` o `revoke`), `COMUNI_PLATFORM_OPERATOR_CHANGE_TICKET`, `COMUNI_PLATFORM_OPERATOR_APPROVER`. Quoted psql variables (`:'var'`), `SET LOCAL` e validazioni formato impediscono l'iniezione SQL; il testo sensibile non viene stampato dall'esecuzione normale.
3. Prima di ogni esecuzione **una persona con titolo autorizzativo e un approvatore indipendente** devono verificare documentazione dell'incarico, Identity Provider attendibile HTTPS, `iss` e `sub` esatti dell'account, appartenenza effettiva e requisito MFA sull'IdP. Il ticket esterno documenta autorizzazione, scoperta OIDC, revisore, data, evidenze e rollback. Lo script valida **solo il formato** dei riferimenti, non firma né prova di identità/MFA. Non effettuare alcun enrollment reale dalla CI o dalla SPA; non automatizzare il bootstrap dell'IdP.
4. Ogni mutazione è una sola transazione PostgreSQL. `pg_advisory_xact_lock(hashtextextended(issuer || chr(31) || subject,0))` serializza due enrollment concorrenti **prima** della riga; `SELECT ... FOR UPDATE` blocca un operatore già presente. `enroll` nuovo crea una riga attiva, audit `platform.operator.enrolled`; `revoke` di uno sconosciuto rifiuta; `revoke` di un attivo disattiva con `platform.operator.revoked`; `enroll` di un disattivato riattiva con `platform.operator.reactivated`. Retry dello **stesso stato** è no-op senza doppio audit. Reimpiegare il medesimo change ticket su due transizioni diverse dello **stesso operatore** è vietato: serve una nuova approvazione, verificata esternamente.
5. La tabella audit non include `iss`, `sub`, approver o nome persona. Conserva `actor_subject=db-owner:<current_user>`, `resource_type=platform.operator`, `resource_id=operator_id`, `correlation_id=operator:<ticket>` e timestamp. Il ticket **non deve** contenere dati personali. `comuni_app_runtime` non ha diritti diretti su roster **né audit globale**, e mantiene esclusivamente `EXECUTE` su `platform.is_active_platform_operator(text,text)`; le API comunali, RLS, la singola API .NET/React e il catalogo moduli non cambiano.
6. TDD con xUnit, PostgreSQL 17 e `psql` reali: enrollment e revoca con effetto dalla richiesta API successiva (OIDC RSA simulato), due richieste concorrenti, idempotenza, reactivation, ticket distinto, input malevoli, tenant isolation, denial runtime e trigger anti-tampering. CI di tutti i sette job su `main` è gate per `completed`.

## Limiti

Lo script owner-only è un **runbook amministrativo**, non un'autorizzazione granulare applicativa: chi possiede il DB owner può anche modificare schema e trigger. Audit append-only SQL non significa immutabilità crittografica o conservazione conforme. Approver/ticket non sono verificati dal software, la firma OIDC/MFA non viene interrogata durante il provisioning; servono verifica umana e amministrazione privilegiata esterna al repository. La revoca blocca le **nuove** richieste `/platform/session`, non revoca access token già emessi né interrompe transazioni già in volo, e non sostituisce un revocation policy dell'IdP. Non esistono ancora console platform, endpoint di modifica di Comuni, impersonificazione, enrollment UI, provider Azure live, RBAC platform, operazioni SPID/CIE o conformità GDPR/AgID verificate. Le epiche #2/#4/#5/#10 restano aperte.

## Emendamento al canale di input (#97 / ADR 0081)

La menzione originaria delle variabili \`psql :'var'\` descrive la prima versione del flusso. Per mitigare il logging di issuer/sub come SQL literal, la procedura attuale legge i cinque \`COMUNI_PLATFORM_OPERATOR_*\` tramite client-side \`\\copy\` e TEMP table, con allowlist nel helper, secondo ADR 0081. L'owner-only, l'audit append-only globale, i lock, la verifica esatta del principal e l'idempotenza stabiliti qui restano invariati. Il payload COPY è reversibile: la prova PostgreSQL 17 non attesta i log Azure/pgAudit/SIEM, né prova l'identità o il mandato dei revisori (#86/#84/#92).
