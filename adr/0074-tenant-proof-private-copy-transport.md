# ADR 0074 — Trasferimento client-side COPY per le chiavi private RLS PostgreSQL

- Data: 2026-11-17.
- Stato: Accepted per test sintetici PostgreSQL 17 / CI; **non autorizza chiavi reali o rollout Azure**.
- Issue: #90, sotto-incremento di #89 e #86; segue ADR 0040 (retirement), ADR 0073 (#88), ADR 0018 e ADR 0022.
- Documentazione ufficiale: [PostgreSQL 17 psql COPY](https://www.postgresql.org/docs/17/app-psql.html), [PostgreSQL 17 COPY](https://www.postgresql.org/docs/17/sql-copy.html), [PostgreSQL 17 logging](https://www.postgresql.org/docs/17/runtime-config-logging.html), [PostgreSQL 17 password authentication](https://www.postgresql.org/docs/17/auth-password.html).

## Problema e threat model

Le procedure `provision-tenant-proof.sql` e `stage-tenant-proof-key.sql` interpolavano `TENANT_PROOF_KEY` tramite `psql :'variable'` nel testo SQL inviato al server. Il quoting previene injection, **non** il logging di plaintext in `log_statement=all`, `log_min_error_statement`, audit SQL/estensioni. Questa chiave firma le prove RLS: una sua esposizione consentirebbe potenzialmente di creare proof per altri Comuni sotto runtime e viola il confine di isolamento. Non basta fissare `log_parameter_max_length=0` o disattivare logging: un auditor deve vedere l'azione senza raccogliere il materiale di firma.

## Decisione tecnica (#90)

1. **Ambito limitato a due script owner-only.** Non cambiare `platform.verified_tenant_id()`, formato HMAC, API, utente runtime, grants, RLS, chiavi esistenti, Azure, Terraform o Key Vault. Le procedure eseguono direttamente su PostgreSQL da runner privato, con checkout e Python3 attendibili, sessione schema-owner e `psql -X -q -v ON_ERROR_STOP=1`. Lo script Python non deve essere invocato da terminale o con output registrato.
2. Estendere la **fixed allowlist** di `scripts/postgres/stream-private-input.py` con soltanto:
   - `tenant-legacy`: `TENANT_PROOF_KEY` (bootstrap);
   - `tenant-stage`: `TENANT_PROOF_KEY_ID` e `TENANT_PROOF_KEY` (nuova chiave versionata).
   L'helper legge solo le variabili attese, rifiuta mancanze, stringhe vuote, valori/envelope troppo grandi e operazioni ignote; errore e codice d'uscita sono statici. Trasmette **un solo** record base64(JSON) ASCII da stdout al solo client `psql`. Non includere altre variabili ambiente, URL, nomi di Comune o credenziali DB.
3. In **un'unica transazione**, creare `pg_temp.comuni_private_input(payload text NOT NULL) ON COMMIT DROP`, poi eseguire il comando client-side e fisso `\\copy ... FROM PROGRAM 'python3 scripts/postgres/stream-private-input.py tenant-legacy|tenant-stage' WITH (FORMAT csv)` (due literal comandi distinti per script). Il server vede l'istruzione `COPY ... FROM STDIN` e SQL che legge dalla tabella temporanea, non un `INSERT ... 'secret'` con il segreto. Un `DO` PL/pgSQL usa `convert_from(decode(payload, 'base64'),'UTF8')::jsonb` e controlla esattamente un record; il materiale si mantiene solo in memoria transazionale/temp e nelle tabelle private finali previste.
4. **Owner-only:** controllare `current_user` con l'owner effettivo di `platform.tenant_proof_secret` e `platform.tenant_proof_keys` per bootstrap, owner di `tenant_proof_keys` per staging. L'account runtime non può alterare materiale. La lunghezza minima è 32 byte (non 32 caratteri). Nel bootstrap `legacy` usare `ON CONFLICT DO NOTHING` e **verificare** il valore già scritto e la sua non-revoca/non-scadenza; non sovrascrivere né ripristinare chiavi obsolete.
5. Nello staging con ID regolato da `^[a-z][a-z0-9_-]{0,31}$` e diverso da `legacy`, prendere `SHARE ROW EXCLUSIVE` su `platform.tenant_proof_keys` nella medesima transazione per serializzare staging contemporanei e `retire-tenant-proof-key.sql`. Inserire solo se assente, verificare identità del materiale, validità temporale e `revoked_at IS NULL`, negare collisioni, revoche/expiration/replay differente. Niente automatismi di rotazione su Azure o rilascio di nuove versioni.
6. **Test-first RED → GREEN**: `tests/infra/test_private_psql_copy.py` nega SQL literal e richiede helper allowlist + fixed COPY; `tests/backend/Comuni.Api.Tests/TenantProofPrivateCopyTests.cs` verifica contro PostgreSQL 17 e `psql` reali idempotenza, mismatch, expired/revoked, runtime negato, input invalidi, staging concorrenti e verifiche delle due chiavi private. Esegue un `sub`-equivalente **canary sintetico** come key con SQL-like e `PGOPTIONS=log_statement=all` e logging parametri massimale, legge i log del container PostgreSQL per verificare `statement: COPY` e assenza di plaintext. RLS/proof, Playwright, SCA, CodeQL e Docker in CI 7/7 sul **medesimo SHA**.
7. I due script di provisioning delle **password PostgreSQL** non rientrano in questa slice; richiedono uno studio distinto di `CREATE/ALTER ROLE PASSWORD`, SCRAM e logging DDL: [#91](https://github.com/KeyserDSoze/Comuni/issues/91). **#89 e #86 rimangono aperte**, insieme ai restanti psql literal e all'audit SIEM/Key Vault, finché ogni criterio non è raggiunto.

## Limitazioni, minacce residue e runbook

**Base64 non cifra.** Il processo Python, l'output stream al client `psql`, il protocollo COPY, la temp table e lo script `DO` possono contenere il materiale in chiaro o reversibile. I test riguardano i **log di istruzioni PostgreSQL 17 in CI**, non pgaudit che registra query nested, estensioni, CSV COPY error context, key dump, process memory, APM o network tap. Non dichiarare GDPR, sicurezza del Key Vault o Azure VNet verificati. Non usare `psql -a/-e`, `set -x`, debug SQL/client, `\copy ... TO STDOUT` o la chiamata diretta del programma di input. Impostare TLS VerifyFull privato con verifica della CA, gestione dei segreti mediante canale autorizzato e audit operatore, retention/monitoring esterni prima dell'impiego reale.

Il repository locale deve essere la **working directory di `psql`**: `\\copy FROM PROGRAM` esegue Python sul client, con path relativo fisso `scripts/postgres/stream-private-input.py`; non sul PostgreSQL server. Un errore nel programma o input mancante blocca lo script `ON_ERROR_STOP=1` e la connessione effettua rollback, senza inserire chiavi. Mai stampare le variabili o catturare stdout della sorgente COPY. Per rollout reale/rotazione HMAC multi-replica mantenere aperte #19 e #6, e per il livello superiore di segretezza/logging #86/#89/#91. La verifica sintetica non costituisce autorizzazione alla produzione.
