# ADR 0102 — pgAudit metadata-only sulle procedure owner-only di revoca Admin e sospensione Comune

- Data: 2026-11-20.
- Stato: **Accepted per hardening e verifica sintetica PostgreSQL 17+pgAudit**; nessuna autorizzazione ad applicare modifiche su Comuni reali.
- Issue: #118; parent #86/#92, dipendenze #84/#5/#6.
- ADR precedenti: 0070 (revoca Admin/ultimo Admin), 0080 (revoke COPY), 0082 (organization lifecycle COPY), 0088 (inventario owner-only), 0098 (SCRAM log), 0099/0100 (rischio pgAudit parameter-on), 0101 (onboarding a due Admin).
- Riferimenti tecnici: [pgAudit README](https://github.com/pgaudit/pgaudit/blob/main/README.md), [PostgreSQL 17 logging](https://www.postgresql.org/docs/17/runtime-config-logging.html), [PostgreSQL 17 psql COPY](https://www.postgresql.org/docs/17/app-psql.html).

## Problema e threat model

I valori di UUID Comune, OIDC issuer/sub, ticket approvazione, reviewer e reason code sono input di due procedure amministrative owner-only che operano sullo stato del Comune e sulle membership. Sebbene il client usi già `\\copy ... FROM PROGRAM` con script statico e trasporto reversibile base64(JSON), le statement PL/pgSQL annidate possono riportare i valori nei log `pgaudit.log_parameter=on`. La issue #116 ha dimostrato una fuga effettiva di un canary sintetico nel server log durante l'onboarding del primo Admin con il medesimo profilo. Sospendere un Comune o revocare un Admin è un'operazione sensibile che deve restare **auditata** senza pubblicare identità o motivi nei parametri.

## Decisione

1. Aggiungere un guard SQL **prima della TEMP e del COPY** nelle transazioni di `revoke-admin.sql` e `set-organization-suspension.sql`. Se `lower(coalesce(current_setting('pgaudit.log_parameter', true),'off')) = 'on'`, l'operazione termina con errore statico. Nessun dato viene ricevuto dal producer, nessun DML viene eseguito e nessuna membership/organization viene mutata. Con PostgreSQL di test che non ha l'estensione installata la GUC mancante non equivale arbitrariamente a `on`; questo non è un lasciapassare alla produzione.
2. **Non cambiare la semantica amministrativa**: owner-only e controlli sulle tabelle, lock organization, isolamento dei Comuni, revoca soltanto con almeno un altro Admin OIDC valido, idempotenza esatta, audit append-only e gestione sospensione/riattivazione rimangono invariati. Nessun `SECURITY DEFINER`, migrazione, GRANT, ruolo, feature flag, endpoint API o applicazione frontend.
3. Nello stesso cluster PostgreSQL 17 **reale** usa-e-getta con pgAudit, dopo onboarding dei due Admin, eseguire `revoke-admin.sql` sul secondo Admin e `set-organization-suspension.sql` con `suspend`. Ogni procedura deve rifiutare la sessione con `pgaudit.log_parameter=on` **prima del COPY**; il percorso valido usa `pgaudit.log_parameter=off`, lasciando `pgaudit.log=role,ddl,write,function`, `log_statement=all` e i parametri nativi di logging massimo attivi. Gli script di provisioning SCRAM sono testati separatamente con parameter-on e redazione ROLE/DDL.
4. Verificare con SQL **statico e senza valori sintetici interpolati**: una organization activated+suspended, modulo Protocollo disabilitato, due Admin OIDC storici (uno attivo, uno inattivo), precisamente sei audit di owner registration, first Admin, activation, second Admin, revocation, suspension. Il rigioco della revoca e della sospensione non deve produrre altri audit; tentare di revocare con un nuovo ticket l'**ultimo** Admin deve fallire con errore atteso senza modificare dati.
5. Il gate legge log Docker e output `psql` soltanto in memoria, nella finestra dopo snapshot iniziale. Richiede sei blocchi `DO`, eventi `FUNCTION,DO`, `WRITE,INSERT`, `WRITE,UPDATE` e almeno sei `statement: COPY`, senza **alcuno dei 22 canary sintetici** (org, name, iss/sub, ticket, approvatori, reason). I failure message sono generici con categoria/canale, mai query SQL, password, valori o log raw. I test Python in `tests/infra/` coprono la perdita anche di un solo COPY o la comparsa di un singolo canary.
6. TDD **RED → GREEN su `main`**: test-first commit [7dd9538](https://github.com/KeyserDSoze/Comuni/commit/7dd95388531ea5fc4db631e0ec371805603e17e1), [Actions 44728763479](https://github.com/KeyserDSoze/Comuni/actions/runs/44728763479), **8 failure attesi** dei nuovi test statici/integrazione nel gate Terraform/Python. Green comprende soltanto i due guard, fixture PostgreSQL17/pgAudit, test e documentazione. Completamento issue #118 **solo dopo 7/7 job Actions verdi sul medesimo SHA finale di `main`**, con xUnit, Playwright, scansioni, Terraform e Docker.

## Rischi residui e approvazione all'esercizio

Il controllo **non** dimostra riservatezza del payload COPY base64(JSON) o tabella TEMP, memoria dei processi, log dei proxy, error context alternativi, Azure Flexible Server, `pgAuditLogToFile`, APM/SIEM, retention, accessi DBA o autenticazione di un reviewer reale. Un `sub` OIDC non è un token crittografico: la verifica di identità/membership richiede IdP e mandato esterni; la revoca di membership non revoca token/sedute presso l'IdP e la sospensione non interrompe richieste già in corso. Le issue #86 e #92 rimangono **OPEN** per le altre procedure owner-only, Azure/SIEM, revisione Security/Privacy/Legal, e #84 per il recovery emergenziale. L'inventario esistente ha ancora 14 trasporti: questa ADR copre soltanto sei procedure owner-only finora verificate; nessun deployment o credenziale live.
