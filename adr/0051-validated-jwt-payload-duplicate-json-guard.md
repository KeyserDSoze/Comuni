# ADR 0051 — Rifiuto fail-closed di proprietà JSON duplicate nel payload JWT validato

- Stato: Accepted per il JwtBearer attualmente in uso e test sintetici HS256/RS256, non certificazione di IdP reali.
- Data: 2026-11-16.
- Issue: #58, dipende da #57 (ADR 0050), epiche #2 e #5.
- Fonti: [RFC 7519 §4 JWT Claims — unique claim names](https://www.rfc-editor.org/rfc/rfc7519#section-4), [RFC 8259 §4 JSON Objects](https://www.rfc-editor.org/rfc/rfc8259#section-4), [ASP.NET Core JWT bearer authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication), [ASP.NET Core JwtBearerEvents.OnTokenValidated](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.jwtbearer.jwtbearerevents.ontokenvalidated).

## Rischio confermato, confine e priorità

La #57 ha reso univoco il `ClaimsPrincipal` comunale e platform: `organization_id/sub/iss` non possono comparire due volte nei claim materializzati. Tuttavia, la rappresentazione **JSON originale** può includere due proprietà con lo stesso nome prima di essere deserializzata dal parser dei token. L'RFC JWT richiede claim names unici; secondo l'implementazione, i parser possono scegliere l'ultima occorrenza e perdere il duplicato. I test RED con **JWT compatti validamente firmati** da HMAC di test e chiave RSA/JWKS test hanno osservato `200 OK` per alcune duplicazioni identiche e `403` per un organization ID discordante, non `401`: l'accettazione della struttura è un difetto di sicurezza reale di questa configurazione, non un'ipotesi astratta. Un token validamente firmato non dovrebbe produrre interpretazioni dell'identità che dipendano dall'ordine dei campi JSON.

## Decisione

1. **Preservare la validazione crittografica esistente.** Non scrivere un nuovo handler OAuth, non usare una nuova libreria per verificare la firma, non leggere Authorization header per scegliere l'identità. `AuthenticationConfiguration.Apply` continua a configurare JwtBearer per firma, issuer, audience, scadenza, firma algoritmica RS256 in hosted e HS256 esclusivamente nei test/demo. Aggiunge `JwtBearerEvents.OnTokenValidated`: l'evento avviene dopo la validazione esistente, prima che una `ClaimsPrincipal` diventi attendibile per le policy.
2. **Rianalizzare la serializzazione del SecurityToken validato.** `JwtPayloadDuplicatePropertyGuard.IsAcceptable` prende soltanto `JsonWebToken.EncodedToken` oppure `JwtSecurityToken.RawData` ricevuto da JwtBearer; se il tipo non è noto o la forma compatta non ha esattamente tre segmenti, fail closed. Decodifica il segmento payload via Base64Url e lo legge con `System.Text.Json.JsonDocument` senza conversioni in `Dictionary`. Per ogni oggetto JSON (anche dentro array e nested), richiede nomi unici con `StringComparer.Ordinal` sulla forma *unescaped* di `JsonProperty.Name`. Quindi `sub` e `\\u0073ub` vengono riconosciuti come il medesimo nome, mentre i diversi casing JSON conservano semantica distinta. Non si ispezionano valori/subject se non per il parsing strutturale.
3. **Risorse bounded e non-disclosure.** Il payload deve essere un singolo oggetto JSON valido, non un array; profondità massima **32**, dimensione decoded **64 KiB**, senza commenti né trailing commas. Errore di parsing, malformazione, duplicazioni o dimensione oltre il limite causano `context.Fail` con un **messaggio costante**, mai con dati raw del JWT, issuer, organization, token o exception. Questi vincoli possono rifiutare un JWT altrimenti correttamente firmato da un IdP configurato: è una scelta fail-closed, da concordare nel deployment reale. Nessuna opzione o flag runtime permette un bypass.
4. **Difesa in profondità con #57.** Dopo il controllo strutturale, `VerifiedPrincipalIdentity` richiede ancora identità unica in `ClaimsPrincipal`, membership PostgreSQL attiva con binding dell'issuer, Comune operativo, e RLS firmata; il Superadmin non riceve organization_id e richiede un roster/operator SQL indipendente. Duplicati nelle proprietà JSON diventano **401 autenticazione negata**, non `403` né `200`.
5. **TDD red/green e nessun Azure live.** RED con JWT sinteticamente firmati a mano (HS256 Testing, RSA RS256 OIDC static JWKS); firma corretta e token valido con duplicati identici/discordanti, nested, Unicode escape, oversized, commenti/trailing commas. GREEN implementazione minima dell'evento + parser bounded, poi regressione 200 di token validi, policy OIDC RS256 invariata, suite totale xUnit PostgreSQL17/.NET10, React/Playwright, Terraform/Python, CodeQL C#/JS-TS, SCA NuGet/npm e build Docker. Solo dopo 7/7 sulla HEAD di `main` chiudere #58.
6. **Limiti e attività successive.** Non è un'attestazione della conformità RFC di token provider esterni, né un test contro un vero Identity Provider/MFA, SPID/CIE o revocation; non analizza token in formato alternativo non usato dall'API. Un provider che emette token oltre i limiti va analizzato esplicitamente, senza abbassare silenziosamente il controllo. Nessuna modifica allo State Terraform, Key Vault, PostgreSQL, segreti o al sistema di migrazione Azure (#49 rimane aperta).

## Alternative respinte

- Fidarsi solo di `ClaimsPrincipal.FindAll`: il parser può aver già eliminato l'informazione sui duplicati.
- Verificare i duplicati `organization_id/sub/iss` **prima** della firma direttamente sull'header HTTP e accettare il risultato come identità: rischia un bypass della validazione. Il guard usa **il token validato** nell'evento post-crypto.
- Accettare l'ultima occorrenza o normalizzare duplicati identici: non è fail-closed e crea interpretazioni diverse tra componenti.
- Logging dei JWT per risolvere incidenti: espone dati personali, token e potenzialmente autorizzazioni impersonificabili.
