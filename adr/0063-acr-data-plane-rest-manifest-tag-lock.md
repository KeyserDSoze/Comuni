# ADR 0063 — Metadati e doppio lock ACR via OAuth2 REST data-plane, senza ARM control-plane

- Data: 2026-11-16.
- Stato: **Accepted per implementazione CI/offline**. Il funzionamento del repository ACR live, i permessi effettivi e la propagazione dei lock **non sono stati provati**.
- Issue: #74, sotto #72/#70/#65/#6. Sostituisce gli adapter Azure CLI di ADR 0056 e 0059, conservandone i contratti di sicurezza. Integra ADR 0062.
- Specifiche ufficiali: [Azure ACR OAuth2 Entra](https://github.com/Azure/acr/blob/main/docs/AAD-OAuth.md), [ACR token repository-scoped](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/authentication/exchange-acr-refresh-token-for-acr-access-token?view=rest-registry-dataplane-2021-07-01), [Get Tag Properties](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/container-registry/get-tag-properties?view=rest-registry-dataplane-2021-07-01), [Update Tag Attributes](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/container-registry/update-tag-attributes?view=rest-registry-dataplane-2021-07-01), [Get Manifest Properties](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/container-registry/get-manifest-properties?view=rest-registry-dataplane-2021-07-01), [Update Manifest Properties](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/container-registry/update-manifest-properties?view=rest-registry-dataplane-2021-07-01).

## Motivazione

Il rilascio ACA (#64) confronta il digest del **Docker push eseguito dal job** con il digest del tag nel registry prima di costruire il piano Terraform. Successivamente (#68) blocca con write/delete disabled **sia il tag commit sia il manifest OCI**, prima di scan CVE, attestazioni firmate e deploy della candidata a 0%. I due adapter Python usavano `az acr manifest show-metadata` e `az acr repository update/show`: tali CLI possono effettuare lookup ARM control-plane incompatibili con il principal GitHub OIDC builder dotato soltanto di `AcrPush`. Concedere `Contributor`/Owner al builder per far funzionare queste CLI comprometterebbe il confine RBAC di #69.

I REST endpoint **data-plane del registry** offrono le operazioni di lettura e modifica dei soli oggetti `/acr/v1/comuni/_tags/<sha>` e `/acr/v1/comuni/_manifests/sha256:<digest>` nel formato JSON strutturato. La verifica dei campi delle risposte è altrettanto importante dell'uso di un URL HTTPS: un JSON che indichi un'altra repository, host o digest deve essere rifiutato anche quando la risposta HTTP è 200.

## Decisione

1. Introduzione di `scripts/azure/acr-registry-data-plane.py` come client OAuth2 HTTPS condiviso dai due adapter `resolve-pushed-image-digest.py` e `lock-approved-image.py`. Il workflow fornisce `--tenant-id "$ARM_TENANT_ID"` dal GitHub Environment protetto oltre a nome/host ACR. Il client accetta solo `registry_name` ASCII lowercase alfanumerico 5–50, `<registry_name>.azurecr.io` esatto, UUID tenant, source SHA lower 40-hex, digest `sha256:` con 64 hex lower. Non legge host/tenant/scope da input HTTP o dal Terraform plan.
2. Autenticazione data-plane in memoria sotto il principal OIDC di build **già controllato** da `check-azure-oidc-session.py`: `az account get-access-token --resource https://containerregistry.azure.net --query accessToken -o tsv` (unica CLI Azure chiamata dagli adapter), `POST https://<ACR>/oauth2/exchange` per ACR refresh token e `POST https://<ACR>/oauth2/token` con `grant_type=refresh_token`, `service=<ACR>`, `scope=repository:comuni:pull,push` per un **access token limitato a una repository**. Non utilizzare scope `registry:catalog:*`, repository esterne, credenziali permanenti o CLI ARM. La capacità del principal `AcrPush` di eseguire in **realtà** i PATCH dev'essere verificata nel registry autorizzato: un token con scope richiesto non conferisce diritti non posseduti.
3. Tutte le chiamate sono HTTPS con verifica certificati della libreria Python, timeout finito, dimensione massima 64 KiB per risposta, status HTTP **200** obbligatorio e redirect disabilitati anche verso lo stesso host. L'header `Authorization: Bearer` è presente soltanto nei GET/PATCH su path allowlisted; per l'autenticazione si usa form body, mai URL query o argv dei token. Output e stderr Azure, HTTP, JSON, token ed error details **non vengono mai pubblicati nei log**; failure con messaggi statici e stop del rilascio. JSON con chiavi duplicate è rifiutato.
4. Il resolver conserva il parsing rigoroso del receipt dello **specifico** `docker push` (un solo digest SHA256 canonico del tag `comuni:<GITHUB_SHA>`) e verifica `GET /acr/v1/comuni/_tags/<sha>?api-version=2021-07-01`. Richiede esattamente `registry=<managedACR>`, `imageName=comuni`, `tag.name=<GITHUB_SHA>`, `tag.digest == push digest` e campi booleani `changeableAttributes` con lettura abilitata. Solo allora scrive le due variabili GitHub `TF_VAR_image=<ACR>/comuni@sha256:<digest>` e `CANDIDATE_IMAGE_DIGEST=sha256:<digest>`. Nessun tag viene passato a Terraform.
5. Il gate di lock richiede l'URI OCI approvata, ripete il **GET tag prima di qualsiasi mutazione**, quindi `PATCH /acr/v1/comuni/_tags/<sha>` e **separatamente** `PATCH /acr/v1/comuni/_manifests/sha256:<digest>`, ciascuno con il solo body JSON `{"writeEnabled":false,"deleteEnabled":false}`. I PATCH devono restituire 200 e JSON con repository/oggetto/digest e attributi coerenti. Infine GET read-back di **entrambi** gli oggetti con booleani `writeEnabled=false, deleteEnabled=false, readEnabled=true` e digest del tag **ancora esattamente** uguale a quello del push. Mai bloccare tutta la repository `comuni`, non abilitare write/delete né effettuare unlock automatico su errore. Se uno dei due update è stato eseguito e il successivo fallisce, la diagnosi e l'eventuale intervento owner sono separati.
6. L'identità build conserva solo il principal GitHub OIDC separato dalla UAI `AcrPull` e dalla fase infra Terraform/Key Vault; il workflow mantiene scan Trivy, SBOM SPDX, attestazioni SLSA/Sigstore, gate Terraform di OIDC/segretazione/RLS e split stable 100% candidate 0%. Nessun `terraform apply` live in questo incremento.

## Test RED→GREEN e limiti

- `tests/infra/test_acr_registry_data_plane_rest.py`: falso client HTTPS e `az account get-access-token`, ordini e URL esatti di exchange/token/GET/PATCH, scope `repository:comuni:pull,push`, token Bearer, wrapper JSON tag/manifest, host/sha/digest malformati, status/redirect/tampering.
- `tests/infra/test_aca_pushed_digest.py`: mantiene i casi adversariali del push receipt, digest mismatch, output env non modificato al failure; finto registry data-plane al posto di `az acr manifest`.
- `tests/infra/test_aca_acr_tag_manifest_lock.py`: mantiene fail-closed/lock duale con fault injection nel REST, status/digest/attrs spoofati e nessun path repository-wide.
- Tutti i **7 job CI** sullo stesso SHA finale di `main` sono richiesti alla chiusura #74: Terraform/Python, .NET10/PostgreSQL, React/Playwright, CodeQL C#/JS, SCA NuGet/npm e Docker.

**Non dichiarare certificazione Azure o sicurezza completa:** i fake HTTPS/CLI non attestano il comportamento reale degli endpoint, gli effettivi scope, il token emesso dall'ACR o se il principal con solo `AcrPush` possa modificare gli attributi lock. È necessaria una prova live **autorizzata e non distruttiva** con registry test e review owner, prima di sbloccare la #72; #70 per credenziali FIC/job split, #65 per supply chain trusted e #6/#49 per go-live e secret. Non ampliare i ruoli per aggirare un 401/403. Non è stato letto né modificato alcun secret Azure.
