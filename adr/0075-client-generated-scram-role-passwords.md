# ADR 0075 — Provisioning dei ruoli SQL con verificatore SCRAM-SHA-256 generato dal client

- Data: 2026-11-18.
- Stato: Accepted per PostgreSQL 17 sintetico e automazioni locali/CI; **non prova la privacy dei log Azure/pgaudit né autorizza credenziali reali**.
- Issue: [#91](https://github.com/KeyserDSoze/Comuni/issues/91), completa la parte password di #89 e segue ADR 0073/#88, ADR 0074/#90. #86 (protezione log di tutte le procedure) resta distinto.
- Fonti PostgreSQL: [ALTER ROLE 17](https://www.postgresql.org/docs/17/sql-alterrole.html), [Password authentication/SCRAM 17](https://www.postgresql.org/docs/17/auth-password.html), [psql 17](https://www.postgresql.org/docs/17/app-psql.html), [logging 17](https://www.postgresql.org/docs/17/runtime-config-logging.html). [pgAudit upstream](https://github.com/pgaudit/pgaudit) per rischi di logging di DDL annidato.

## Minaccia e decisione

Il precedente `scripts/postgres/provision-runtime-role.sql` e `provision-platform-read-role.sql` usava `\\getenv`, SQL `:'password'`, poi `SELECT format('CREATE/ALTER ROLE ... PASSWORD %L',secret) \\gexec`. Il plaintext arrivava quindi **come literal nel testo SQL** al server, visibile potenzialmente a `log_statement=ddl/all`, `log_min_error_statement`, session audit, SIEM. Il quoting impedisce SQL injection ma non il logging. Anche un normale `INSERT` parametrizzato può essere registrato, se `log_parameter_max_length` consente i valori.

1. L'helper client-side `scripts/postgres/stream-private-input.py` aggiunge due operazioni allowlist **fisse**: `runtime-role` legge soltanto `RUNTIME_DB_PASSWORD`, `platform-role` legge soltanto `PLATFORM_READ_DB_PASSWORD`. La password deve essere ASCII stampabile: minimo **24** caratteri per runtime, **32** per platform, massimo 1024 byte; nessun whitespace di controllo e nessun Unicode (limitazione intenzionale per evitare una SASLprep diversa fra client Python e server). Input assente/corto/non stampabile/eccessivo fallisce con errore statico senza contenuti. La password non è inserita nel JSON del trasporto.
2. Il **client** calcola per ogni invocazione un nuovo verificatore PostgreSQL `SCRAM-SHA-256$4096:salt$StoredKey:ServerKey` conforme al formato PG17: salt casuale `secrets.token_bytes(16)`, `hashlib.pbkdf2_hmac('sha256',password,salt,4096)`, ClientKey `HMAC(saltedPassword,'Client Key')`, StoredKey `SHA256(ClientKey)`, ServerKey `HMAC(saltedPassword,'Server Key')`; codifica base64 standard. Il segreto in chiaro **rimane sul client**. Una ripetizione della procedura genera un sale nuovo, persino se la password è uguale: cambia l'hash ma non le credenziali effettive del login. L'algoritmo richiede client e server compatibili con SCRAM; per salt e iterazioni diversi, aggiornare ADR/test secondo la versione PostgreSQL supportata.
3. I due script owner-only richiedono `current_user` proprietario della risorsa di riferimento (`platform.organizations` per runtime, `platform.platform_organization_inventory` per reader). Una tabella `pg_temp.comuni_private_input` `ON COMMIT DROP` riceve un unico record base64(JSON) via **`\\copy ... FROM PROGRAM` client-side statico** con payload che contiene **solo `SCRAM_VERIFIER`**, mai plaintext. Il blocco `DO` verifica la forma del verifier, controlla che l'account non sia privilegiato/inherited e usa `EXECUTE format('CREATE/ALTER ROLE ... PASSWORD %L', v_verifier)` per l'operazione DDL. `\\gexec` e `:'password'` sono eliminati; `GRANT CONNECT` è eseguito dentro un `DO` senza password. Le modifiche DDL/grants sono nella **stessa transazione** di provisioning e rollback.
4. Il role SQL è **identico**: `comuni_app_runtime` mantiene grants allowlist ai moduli/operazioni approvate, RLS firmata, nessuna ownership/schema CREATE, Admin alterati proibiti; `comuni_platform_reader` può leggere solo la proiezione inventario, il predicato platform OIDC e inserire audit append-only, non dati dei Comuni, né essere superuser. Nessun nuovo utente, grants globali, `SECURITY DEFINER`, API, feature flag, Azure/Terraform apply o migration. `NOSUPERUSER NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` espliciti; un ruolo preesistente elevato o membro di un altro ruolo è **rifiutato** senza autoriparazione.
5. TDD RED: `tests/infra/test_private_psql_copy.py` introduce calcolo/decodifica/verifica indipendente di salt, PBKDF2, StoredKey e ServerKey; assenza del plaintext nel payload; sale diverso nei due retry; password invalide/Unicode non accettate; SQL prive di `:'password'`/`\\gexec` e con `\\copy` statico. `tests/backend/Comuni.Api.Tests/PostgresRolePrivatePasswordTests.cs` esercita via PostgreSQL 17/psql la rotazione temporanea con password sintetiche, **login Npgsql effettivo** dei due ruoli e recupero delle credenziali originali in `finally`, verifica `pg_authid.rolpassword` SCRAM, attributi least-privilege, grants distinti, account runtime negato, input bad/missing e lettura log Docker PostgreSQL usando `log_statement=all`, `log_parameter_max_length=-1` e `log_parameter_max_length_on_error=-1` per verificare `COPY` visibile ma plaintext canary assente. Infrastruttura `test_platform_read_role_contract.py` è aggiornata al nuovo confine (env password soltanto nel client helper). Playwright, Terraform, CodeQL, SCA e build Docker restano gate 7/7 **sullo stesso SHA finale di `main`**.

## Garanzie, rischio residuo, sicurezza operativa

Il trasporto **non è crittografia**: base64 del verificatore è reversibile come formato, anche se StoredKey/ServerKey non equivalgono alla password originale. **Il verificatore SCRAM resta un secret**: chi accede a pg_authid o al verificatore può compiere attacchi offline su password deboli. DDL dynamic SQL in `DO` può essere intercettato da pgAudit, log PL/pgSQL, strumenti DBA, APM o tracciamento di query annidate e mostrare il **verificatore**, anche se non il plaintext. Il meccanismo garantisce solo che il **plaintext** non sia nel payload/DDL o nei log standard verificati in CI con i canary sintetici. Nessuna prova di logging Azure PostgreSQL/SIEM, TLS/mTLS, Key Vault, ruoli di deploy, GDPR, password policy di produzione o rotazione senza downtime; queste dipendono da #86/#5/#6/#38/#49 e approvazione security/privacy.

Runbook offline, **solo fino a review reale**: usare checkout attendibile, directory root del repository, Python3, runner dedicato con segreti da secret store e schema owner PostgreSQL privata TLS VerifyFull. Eseguire `psql -X -q -v ON_ERROR_STOP=1 -f scripts/postgres/provision-runtime-role.sql` o `...provision-platform-read-role.sql`; mai `psql -a/-e`, `set -x`, program stdout a terminale, dumping environment, SQL logging estensioni senza audit di privacy. Non eseguire con ruoli reali finché #86 e verifiche IdP/Azure non sono concluse. Per rollback la rotazione va organizzata separatamente e non riportare in issue credenziali/valori. L'esecuzione del test CI su PostgreSQL disposable non equivale alla release o conformità della PA.
