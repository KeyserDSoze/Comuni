# ADR 0043 — URI Key Vault versionata per la connessione PostgreSQL della sola revisione candidata

- Stato: Accepted per **tooling Terraform/CI offline e staging controllato**, non collaudo Azure.
- Data: 2026-11-16.
- Issue: #50, slice della #49 e dipendenza delle #6/#5/#19.
- Riferimenti: ADR 0017–0019, 0032, 0042; [Azure Container Apps secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets), [Azure Container Apps revisions](https://learn.microsoft.com/en-us/azure/container-apps/revisions), [Npgsql SSL modes](https://www.npgsql.org/doc/connection-string-parameters), [Azure PostgreSQL TLS](https://learn.microsoft.com/en-us/azure/postgresql/security/security-tls-how-to-connect).

## Problema e modello di minaccia

L'unica API .NET usa `comuni_app_runtime` sotto RLS firmata per tutti i Comuni. In Terraform lo storico `azurerm_key_vault_secret.postgres_connection` è creato a partire da `postgres_runtime_password` (valore nel Terraform State); la secret ACA omonima usa un **URI Key Vault versionless** e la connessione ha `SSL Mode=Require`, insufficiente a comprovare il nome host. La connessione è app-scoped e una rotazione in-place può modificare la stable durante il rollout di una candidata. Non si possono migrare password e TLS del runtime in-place senza verificare stable, root CA, PostgreSQL/Key Vault e piano di rollback.

## Decisione

1. **Nuovo secret solo per candidata.** `runtime_postgres_connection_secret_version` è una variabile Terraform **non segreta, obbligatoria, non-null, 32 hex**. La candidata ottiene `ConnectionStrings__Default` dalla nuova secret ACA `pg-<16 hex>` (19 caratteri, entro il limite), che punta esattamente a `secrets/postgres-runtime-connection/<32 hex>` nel **medesimo Key Vault** della chiave tenant-proof; la connessione completa viene predisposta **esternamente a Terraform** con riferimento immutable. Niente nuovi DB, API, frontend o risorse Key Vault gestite per il nuovo valore. La `postgres-connection` della stable e la vecchia risorsa Terraform vengono **conservate senza modifiche** durante il rollout; non si presume che siano sicure.
2. **Gates fail-closed.** GitHub Environment `RUNTIME_POSTGRES_CONNECTION_SECRET_VERSION` fornisce soltanto l'ID della versione. Prima del plan, uno script `az keyvault secret list-versions` valida metadata exact/enabled senza `secret show` o stampa di URI/password. Il plan JSON è soltanto stream tra Terraform e `check-staged-rollout-plan.py`. Il gate impone versione valida e URI pinned in vault approvato, connessione API `secret_name=pg-<16hex>` senza `value`, nessuna modifica/rimozione di secret ACA preesistenti, nessuna collisione con URI diverso del medesimo prefisso e nessun update del legacy `azurerm_key_vault_secret.postgres_connection`. Resta 100% traffico stable / 0% candidata, nessuna modifica alle vecchie versioni HMAC o all'inventario Superadmin.
3. **Verifica post-stage:** `verify-staged-revisions.py` esegue letture metadata delle revisioni esistenti e rifiuta candidata non `Healthy/Provisioned/Running`, image/key ID non attesi, peso traffico alterato o `ConnectionStrings__Default` senza `secretRef=pg-<16hex>`. Non legge la secret o chiama operazioni mutative.
4. **Compatibilità e limiti:** il nuovo valore della connection string **deve** usare `Username=comuni_app_runtime`, il vero FQDN Azure PostgreSQL, lo stesso database, `SSL Mode=VerifyFull;Trust Server Certificate=false`, con CA validabile dall'immagine; il piano Terraform/metadati non possono ispezionare questi contenuti. Un successivo sviluppo #49 deve aggiungere un gate all'avvio backend sulla connessione default in hosted, e l'operatore dovrà testare TLS reale, RLS, pooling e latenza/rollback nella VNet. Lo state Terraform attuale può contenere password runtime storiche e gestisce la vecchia secret: **non** creare la falsa impressione che sia stato sanificato. Un cambio di password Terraform o del segreto legacy deve fallire sul gate prima dell'apply; ma un cambiamento esterno del versionless può ancora incidere sulle stable. Solo una futura procedura approvata può migrare/dismettere il legacy senza outage.
5. **TDD:** test RED offline in `tests/infra/test_runtime_postgres_candidate.py` per contratto Terraform, Key Vault CLI falso, piani di staging hostili e preservazione stable; GREEN su Terraform, preflight, plan gate e verifica live metadata. Suite Python, Terraform validate e gli altri job CI obbligatori sullo SHA finale. Nessun account Azure reale.

## Scelte scartate

Sostituire direttamente `SSL Mode=Require` nel vecchio `azurerm_key_vault_secret.postgres_connection` aggiornerebbe un secret versionless con rischio di restart/stable drift ed è proibito in questa slice. Inserire una nuova password in `TF_VAR_*` o un nuovo `azurerm_key_vault_secret` lascerebbe copie nel Terraform State. Autopromuovere la candidata dal suo stato `Healthy` non prova un accesso RLS multi-tenant. Non inventare né aggirare il requisito di runner owner/Key Vault in VNet e approvazioni.
