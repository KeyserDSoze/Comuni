# ADR 0101 — pgAudit metadata-only per attivazione Comune e enrollment del secondo Admin OIDC

- Data: 2026-11-20.
- Stato: **Accepted come hardening fail-closed su PostgreSQL 17/pgAudit sintetico**; non autorizza tenant o utenti reali in produzione.
- Issue: #117, slice di #86 e #92; collega #84 e le epiche #3/#5/#6.
- ADR precedenti: 0069 (Admin aggiuntivo), 0073/0078 (input COPY), 0083 (activation), 0088 (inventory), 0099/0100 (leak pgAudit sui valori di input del registration/bootstrap).
- Fonti: [pgAudit README: `pgaudit.log_parameter`](https://github.com/pgaudit/pgaudit/blob/main/README.md); [PostgreSQL 17: logging](https://www.postgresql.org/docs/17/runtime-config-logging.html); [PostgreSQL 17: psql COPY](https://www.postgresql.org/docs/17/app-psql.html).

## Contesto

La #116/ADR 0100 ha osservato con PostgreSQL17/pgAudit reale che, quando `pgaudit.log_parameter=on`, un identificativo sintetico del Comune poteva finire nei log del server durante un `DO` owner-only, pur non essendo presente nel testo SQL trasmesso da `psql`. Il trasferimento `COPY FROM PROGRAM` protegge dai literal SQL ma **non impedisce** che il parametro di una statement annidata venga riportato nei log delle operazioni. Due script del percorso di onboarding già collaudati, `register-organization.sql` e `bootstrap-initial-admin.sql`, sono stati protetti da un preflight SQL fail-closed **prima del COPY**.

Il passo successivo presenta lo stesso rischio: `activate-organization.sql` usa UUID Comune, ticket e reviewer, mentre `enroll-additional-admin.sql` usa anche issuer e subject OIDC del secondo Admin, ticket e reviewer. Entrambi già usano il canale privato COPY dell'inventory a 14 procedure, ma **non** rifiutavano il profilo che registra valori pgAudit. Non sono richiesti nuovi script, nuove chiavi o modifiche alle regole di autorizzazione.

## Decisione

1. Aggiungere a **entrambi** gli script un preflight statico subito dopo `BEGIN` e prima della tabella TEMP/`\\copy`: `lower(coalesce(current_setting('pgaudit.log_parameter', true),'off'))='on'` causa errore costante e rollback, senza leggere alcun input sensibile, senza DML e senza inoltrare canary. I controlli owner-only, tenant, membership, locks, current-status, idempotenza, audit e permessi restano invariati. La configurazione pgAudit **senza estensione** nel PostgreSQL 17 applicativo non è equiparata arbitrariamente al profilo on. La policy di esecuzione in ambienti reali va approvata separatamente.
2. Il test integrato nel cluster PostgreSQL17+pgAudit effimero del job backend esegue le **quattro procedure reali**: registrazione Comune pending, primo Admin OIDC, attivazione e secondo Admin OIDC. I dati sintetici sono trasportati soltanto con `stream-private-input.py` e `psql -X -q -v ON_ERROR_STOP=1` con login owner. Il profilo consentito è `pgaudit.log_parameter=off`, mentre restano `pgaudit.log=role,ddl,write,function`, `log_statement=all` e impostazioni native per log dei parametri ed errori. I percorsi dei login SCRAM continuano a essere testati con `pgaudit.log_parameter=on`, mantenendo la redazione ROLE/DDL delle ADR 0076/0098.
3. Testare **anche il profilo vietato** con `on` per activation e Admin enrollment: errore costante prima del COPY, nessuna modifica ad activation/membership/audit; eseguire poi il profilo metadata-only, il retry di entrambe le procedure e un subject aggiuntivo non canonico rifiutato. Dopo tutto deve risultare **esattamente** una organization active e non suspended, protocol disabled, due Admin OIDC active, e quattro eventi amministrativi owner-only (registered, initialized, activated, added). La query di verifica usa **solo testo SQL statico**, senza alcun UUID o subject sintetico nell'argomento di `psql -c`.
4. Lo stesso gate ispeziona i log reali Docker privatamente, senza stampare mai query/valori/verifier: deve vedere i quattro blocchi `DO`, eventi pgAudit FUNCTION, WRITE INSERT e UPDATE e le native `COPY`, rifiutando in tutte le linee qualunque canary di UUID, nome, issuer, sub, ticket/reviewer e input invalidi. La diagnostica usa solo categoria/canale, mai i dati esatti. Il positivo sintetico Python copre anche la rimozione artificiale di un singolo evento COPY o un canary in un solo log/client.
5. TDD **RED prima del codice**: commit `05cb4cd0e03df0a8a43a4d5f6d26ecbf33ec9759`, run [44725718436](https://github.com/KeyserDSoze/Comuni/actions/runs/44725718436), **sei fallimenti attesi** nei test statici Python per guard mancanti e fixture reale incompleta; gli script non erano ancora modificati. GREEN e documentazione nello SHA finale di `main`. Chiudere la #117 **solo** con CI completa 7/7 sul medesimo commit.

## Confini e minacce residue

**Metadata-only non significa audit spento**: il test richiede le classi ROLE/DDL/WRITE/FUNCTION, i log nativi degli statement e la tracciabilità dei quattro eventi applicativi. Il profilo `pgaudit.log_parameter=off` elimina solo il valore dei parametri dal canale pgAudit, non i payload COPY, i dati presenti nel database o gli eventi di amministrazione. Il test osserva una **fixture sintetica**, non PostgreSQL Azure Flexible Server, pgAuditLogToFile, collector, APM, SQL proxy, tracce SQL, error context alternativi, backup, retention o dump. Le parti reversibili del COPY base64(JSON) e la tabella temporanea non sono cifrate. Il reviewer presente in un campo non prova la sua identità, il mandato, MFA o l'indipendenza dell'approvazione. Non introdurre permessi runtime, `SECURITY DEFINER`, deployment Azure o claim di compliance. I dieci script owner-only restanti, insieme alla review completa di logging e privacy/IdP live, rimangono nelle #86/#92/#84/#49/#6.
