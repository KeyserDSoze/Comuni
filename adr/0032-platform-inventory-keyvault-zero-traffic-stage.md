# ADR 0032 — Staging opt-in dell'inventario Superadmin con URI Key Vault versionato, senza connection secret in Terraform

- Stato: Accepted **per tooling e guardrail di staging offline**, non autorizzazione di un ambiente Azure reale (#38)
- Data: 2026-11-15
- Dipendenze: ADR 0011–0019, 0028–0031; issue #5/#6/#10/#19/#37/#38
- Fonti ufficiali: [Microsoft Learn — Manage secrets in Azure Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets), [Microsoft Learn — Troubleshoot deployment errors in Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/troubleshoot-deployment-errors), [Terraform azurerm_container_app](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/container_app)

## Problema

#37 dispone di un secondo login SQL `comuni_platform_reader` e di un endpoint paginato per i soli metadati comunali. È **OFF per default** perché il primo percorso Terraform Azure non provvede a trasferire la stringa di connessione dalla cassaforte al processo della API. Trattandosi di una vista globale che si avvale dei privilegi del proprietario, sarebbe particolarmente rischioso passare la password al Terraform State, riusare la credenziale `comuni_app_runtime` oppure avviare immediatamente la nuova revisione al 100%. I riferimenti Key Vault delle Container Apps sono *application scoped*; un cambio di nome/versione in-place può influire su revisioni ancora attive. Il normale secret latest/versionless può inoltre aggiornarsi automaticamente e causare restart delle revisioni attive secondo la documentazione Microsoft.

## Decisione

1. **Solo metadati in Terraform.** `platform_inventory_enabled` è un input booleano default `false`. Il suo `platform_inventory_secret_version` è un ID Key Vault **esatto a 32 caratteri esadecimali**, default vuoto, mai il valore della password/connection string. Terraform **non** dichiara `azurerm_key_vault_secret` per l'inventario, non legge `data.azurerm_key_vault_secret`, non riceve `TF_VAR_platform_inventory_password` o connection string. Il segreto `platform-inventory-connection` è creato/approvato **all'esterno** di Terraform e lo state deve conservare unicamente l'URI versionato, non il suo valore. Lo state esistente può **ancora** contenere altri segreti storici (#6); non è dunque un'affermazione che lo state completo sia privo di segreti.
2. **Una sola API e un solo PostgreSQL.** Se e solo se il flag è true, `azurerm_container_app.main` aggiunge una secret app-scoped con nome immutabile `platform-read-v<version>`, referenziata mediante la user-assigned managed identity già configurata su Key Vault. La nuova revisione candidata riceve `PlatformInventory__Enabled=true` e `ConnectionStrings__PlatformRead` via `secret_name`, non una variabile `value` in chiaro. Se flag false, `PlatformInventory__Enabled=false`, niente connection env e nessuna nuova secret. Non nascono Container Apps, frontend o database separati.
3. **Opt-in manuale e gate di staging.** Il workflow `Deploy to Azure` (ambiente `production`, approvazione esterna) ha un checkbox `enable_platform_inventory` default false, e ottiene il solo ID versione da `vars.PLATFORM_INVENTORY_SECRET_VERSION`. Quando attivo, un preflight `scripts/azure/check-platform-inventory-secret.sh` verifica *solo* metadati della versione esatta su `az keyvault secret list-versions`: abilità=true, URI preciso, nessun fallback latest e nessun `secret show`. Mancanza di permessi/lista/versione fa abortire prima del plan. Il preflight non conferma il contenuto del secret né la sua corrispondenza al ruolo SQL.
4. **Plan JSON non loggato.** Il workflow continua a inviare il piano in pipe a `scripts/azure/check-staged-rollout-plan.py`. I nuovi `--inventory-enabled`/`--inventory-secret-version` impongono coerenza fra scelta manuale, nome della secret, URI pinned nell'**identico Key Vault** del tenant-proof-key approvato, configurazione del container e assenza di `value` inline. In modalità disabled rifiutano la presenza di `ConnectionStrings__PlatformRead` o `PlatformInventory__Enabled=true`; preservano tutte le app-scoped secrets esistenti e rifiutano aggiunte non approvate. Rimane obbligatorio stable 100%, candidata 0%, no delete/replace né mutazione segreti stable (ADR 0017–0019).
5. **Ruolo SQL solo tramite runner privato owner-reviewed.** Dopo le migrazioni fino a `202611150012_PlatformOrganizationInventory`, un runner con accesso alla rete PostgreSQL privata esegue `scripts/postgres/provision-platform-read-role.sql` con `PLATFORM_READ_DB_PASSWORD` fornita da un gestore segreti autorizzato, distinta da credenziali owner e tenant-runtime. Esaminare lo script, il ruolo e i grant con SQL/runner approvati. Non eseguire automaticamente questa operazione dalla pipeline pubblica di deploy: oggi il runner Actions non ha accesso alla VNet privata né IdP/MFA reale.
6. **Gates live obbligatori non soddisfatti da CI.** Prima di abilitare anche solo la candidata 0% su Azure occorrono: identity e RBAC della managed identity, secret di connessione PostgreSQL creato esternamente con password del ruolo limitato, sessione TLS su VNet privata, hostname/database/username `comuni_platform_reader` corretti, approvazione indipendente, verifica del role `NOSUPERUSER/NOBYPASSRLS` e delle grants di sola vista, test OIDC firmati reali su due tenant sintetici e inventario platform, audit senza PII, monitoraggio e piano rollback. La verifica di staging esistente è solo metadata; la smoke OIDC dell'ADR 0019 è un tool *manuale*, non un'autorizzazione al go-live.

## Alternative respinte

- Inserire `ConnectionStrings__PlatformRead` in `TF_VAR_*`, `azurerm_key_vault_secret.value` o variable sensitive: il valore rimarrebbe nel Terraform State e potenzialmente nel plan. Respinto.
- Usare secret `platform-read` versionless: un nuovo valore potrebbe essere recuperato automaticamente dalle revisioni attive. Respinto.
- Dare accesso globale a `comuni_app_runtime` o connessione owner: SQL injection sul normale percorso tenant bypasserebbe la RLS. Respinto.
- Attivare automaticamente inventario su tutte le revisioni o promuovere latest 100%: non ci sono test IdP/Azure live, né provisioning privato verificato. Respinto.

## Rischi e lavoro successivo

L'URI del Key Vault e la flag sono **metadata** e vanno verificati, non sono un attestato di chi ha installato quale password. Le credenziali `PlatformRead` esisteranno nella memoria del processo API e saranno esposte se l'host viene compromesso; il nuovo account può leggere tutti i metadati della vista e inserire audit, non è isolato per Comune. Non esiste ancora un deploy live, una prova di restore, la verifica del secret contenuto o la rotazione di credenziali senza interruzione con vecchie versioni application-scoped conservate. Le revisioni stable già abilitate all'inventario potrebbero richiedere un input specifico per conservare la vecchia secret durante la rotazione; il gate **deve bloccare** la rimozione fino a un piano formalmente approvato. Una procedura di rollout/recovery live, compresa la gestione credenziali dell'app da Key Vault, appartiene a un'issue separata. Le epiche #5/#6/#10/#19 restano aperte; nessuna conformità GDPR/AgID o disponibilità production viene dichiarata.
