# ADR 0044 — Fail-closed TLS e identità del server PostgreSQL al bootstrap del runtime comunale

- Stato: Accepted per **configurazione API verificata da TDD**, non verifica del canale TLS Azure live.
- Data: 2026-11-16.
- Issue: #51 (sotto #49/#5/#6, dipende da #50); #19 per stage/rollback RLS.
- Riferimenti interni: ADR 0013–0019, 0031–0034, 0041–0043.
- Riferimenti ufficiali: [Npgsql SSL modes](https://www.npgsql.org/doc/api/Npgsql.SslMode.html), [Npgsql connection string parameters](https://www.npgsql.org/doc/connection-string-parameters), [Azure PostgreSQL Flexible Server TLS](https://learn.microsoft.com/en-us/azure/postgresql/security/security-tls), [Azure PostgreSQL TLS how-to](https://learn.microsoft.com/en-us/azure/postgresql/security/security-tls-how-to-connect), [Azure Flexible Server private networking](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private), [TLS certificate troubleshooting](https://learn.microsoft.com/en-us/azure/postgresql/security/security-tls-troubleshoot).

## Problema e minaccia

Il Core della singola API .NET 10 condivide un solo DB PostgreSQL multi-organization e usa login `comuni_app_runtime` con RLS HMAC firmata. Il secret legacy Terraform `postgres-connection` contiene `SSL Mode=Require`, che cifra ma non dimostra l'identità del peer: un DNS/hostname malevolo o un endpoint MITM potrebbe sottrarre le credenziali e impersonare il DB. #50 ha introdotto una **nuova secret esterna versionata** per la sola candidata 0% `pg-<16hex>`, ma il plan gate può leggere soltanto il suo *URI*, non il valore della connection string né il certificato. Serve quindi un contratto di bootstrap che neghi l'avvio se il contenuto del secret non rispetta la politica TLS/identità server.

## Decisione

1. **Un unico confine startup.** `RuntimePostgresConnectionSettings.Read(IConfiguration, environmentName)` legge `ConnectionStrings:Default` e la restituisce inalterata soltanto dopo validazione; `Program.cs` la chiama prima di `PlatformInventorySettings.Read`, della registrazione EF o di qualunque query SQL. I privilegi DB e le policy RLS sono invariati. La configurazione non viene mai riscritta, serializzata o loggata.
2. **Hosted fail closed.** Qualunque ambiente diverso esattamente da `Development` e `Testing` richiede `NpgsqlConnectionStringBuilder.SslMode == VerifyFull` e `TrustServerCertificate == false`; nessuna accettazione di `Disable`, `Allow`, `Prefer`, `Require` o `VerifyCA`. Il ruolo deve essere `comuni_app_runtime`, con password e database non vuoti, porta 5432, e **singolo** FQDN Azure Flexible Server nella forma `<server>.postgres.database.azure.com`, con nome host ASCII conforme; rifiutiamo IP/localhost, aliases VNet diversi dal nome certificato, multi-host e suffissi spoofed. Npgsql parser errors producono solo errori generici, senza testo di connessione, credenziali o dettagli dell'eccezione originaria. Nessun fallback HTTP/JWT né comando di upgrade automatico alla secret stable.
3. **Locale e test.** `Development`/`Testing` richiedono una connessione non vuota ma possono usare PostgreSQL 17 disposable/Compose senza infrastruttura Azure TLS. Non sono consentiti SQLite né un database alternativo; i test xUnit e Playwright preesistenti restano validi. Il contratto Python offline verifica la sequenza di Program e il confine del secret legacy. La RED CI fallisce nelle suite backend e infra, poi la GREEN completa deve passare tutti i job sull'ultimo SHA `main`.
4. **Operatività Azure e limiti.** Azure PostgreSQL raccomanda l'uso del FQDN originale anche con DNS risolto nella rete privata e la verifica delle CA root (non pin leaf/intermediate). `VerifyFull` è compatibile con un DNS privato che risolve quel nome al server reale; l'eventuale vincolo di networking che impedisce di convalidare hostname **non** autorizza downgrade silenzioso a `VerifyCA`: blocca lo stage e richiede una decisione di sicurezza separata. Il bootstrap convalida **metadati di stringa**, non handshake TLS, catena CA disponibile, Key Vault bytes/version matching, password runtime/SQL grants, pooling, RLS dei due tenant o health del server. Occorrono smoke Azure nella VNet con due Comuni sintetici, verifica CA e SAN, readiness, revision label, stable 100%/candidate 0%, tracciamento, approvazione e procedura di rollback.
5. **Stable non toccata e debt.** Questa slice non modifica `infra/main.tf` né `azurerm_key_vault_secret.postgres_connection` e non effettua `terraform apply`. La vecchia secret app-scoped `postgres-connection` può ancora risolvere latest ed essere usata da una stable con il binario precedente; la password rimane in snapshot Terraform storici. Dismissione sicura, migrazione stable e analisi state sono ancora #49/#5/#6, mentre stage e retirement HMAC sono #19.

## Alternative rifiutate

- `SslMode.Require` o `VerifyCA` sotto credenziale runtime: non impone entrambi CA e identità hostname, insufficiente al rischio cross-Comune.
- Restrizione al solo metadata URI Key Vault: non verifica il contenuto della stringa né il trust TLS.
- Riutilizzare `PlatformInventorySettings` o il login `comuni_platform_reader`: sono contesti SQL distinti, con privilegi diversi, e questo nuovo guard deve proteggere anche un Comune senza inventario globale.
- Cambiare in-place la secret legacy o imporre PKI Azure a CI/Development: può spezzare stable e suite locali e non prova un rollout reale.
