# ADR 0062 — Docker login ACR con token OAuth2 Entra data-plane, senza `az acr login`

- Data: 2026-11-16.
- Stato: **Accepted per codice, contratto offline e workflow**. Il funzionamento ACR live e i privilegi effettivi vanno verificati dall'owner.
- Issue: #73, sotto la #72, #70, #65 e #6; estende ADR 0060–0061.
- Fonti: [Microsoft ACR — OAuth2 exchange](https://learn.microsoft.com/en-us/rest/api/registry-dataplane/authentication/exchange-aad-access-token-for-acr-refresh-token?view=rest-registry-dataplane-2021-07-01), [Azure ACR — AAD OAuth flow](https://github.com/Azure/acr/blob/main/docs/AAD-OAuth.md), [Microsoft — ruoli data-plane e control-plane ACR](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-built-in-roles-overview), [Docker login credentials](https://docs.docker.com/reference/cli/docker/login/).

## Contesto e rischio

ADR 0061 (#71) isola temporalmente due principal GitHub federati: uno per infra/Key Vault/Terraform e uno distinto **solo per ACR build/push/lock**. Il gate RBAC #69 impone `AcrPush` diretto e nega ruoli `Owner`/`Contributor` ereditati sul registry. La procedura di build usava `az acr login`; secondo la matrice Microsoft, alcuni comandi `az acr`, incluso il login, richiedono permessi **control-plane** che `AcrPush` non concede. Assegnare al builder `Container Registry Contributor and Data Access Configuration Administrator` abilita anche la modifica o eliminazione dell'ACR: non è accettabile.

Azure documenta un flusso di autenticazione **OAuth2 data-plane ACR** che non richiede il lookup ARM del registry per eseguire Docker login. Un Entra token effimero non viene passato alla shell né scritto su file e viene scambiato via HTTPS per un ACR refresh token. Il token finale viene trasmesso a Docker **esclusivamente via stdin**, non nella command line.

## Decisione

1. Nuovo `scripts/azure/login-acr-oauth.py` invocato dopo **`Verify ACR build CLI OIDC session`** e prima di `docker build/push` nello stesso workflow `deploy.yml` (GitHub Environment `production`, solo `refs/heads/main`). Richiede `--registry-name`, `--registry-host`, `--tenant-id`; il nome ACR deve essere 5–50 caratteri lowercase alfanumerici e l'host deve essere **esattamente** `<nome>.azurecr.io`, senza porte, percorsi o DNS/URL arbitrari. Il tenant ID è un UUID.
2. Sotto la sessione `azure/login` OIDC del build principal **già controllata** da `check-azure-oidc-session.py`, leggere in memoria `az account get-access-token --resource https://containerregistry.azure.net --query accessToken --output tsv --only-show-errors`. La CLI non emette token nei log: stdout/stderr sono catturati e il token è valido solo se formato ASCII non ambiguo, lunghezza limitata e nessun whitespace/carriage return. Il servizio Microsoft Entra/ACR, non il nostro codice, deve validare firma, aud, scadenza e permessi effettivi.
3. Inviare un unico `POST https://<approved-acr-host>/oauth2/exchange` con `Content-Type: application/x-www-form-urlencoded` e parametri `grant_type=access_token`, `service=<approved-host>`, `tenant=<approved-tenant-uuid>`, `access_token=<aad-token>`. **Nessun redirect HTTP ammesso**, incluso 301/302/307/308, per impedire l'esfiltrazione del token su URL arbitrario; TLS HTTPS usa la verifica predefinita di Python. Timeout 20 s, risposta max 32 KiB e status 200 richiesto.
4. Richiedere un unico campo `refresh_token` testuale non vuoto, con formato printable/ASCII e limiti di dimensione; non stamparlo, non scriverlo su disco e non passarlo come argomento. Eseguire `docker login <approved-host> --username 00000000-0000-0000-0000-000000000000 --password-stdin` con il refresh token tramite `subprocess.run(input=...)`. Fallimenti CLI, HTTP, JSON, token, Docker o timeout interrompono la release con **messaggi statici**, senza output AAD/ACR/Docker, access token, refresh token o identificativi del tenant.
5. **Non usare `az acr login`**, nessun fallback con password di service principal o account admin ACR; non allargare lo scope RBAC del principal build. L'accesso Docker resta in cache della Docker CLI per i passaggi successivi (push, Trivy), e il `docker logout` obbligatorio al confine con Terraform (#71) continua a cancellare la credenziale locale. Il digest del push, la firma SLSA/SPDX, la scansione CVE, i gate di lock e il traffico stable 100% / candidate 0% restano invariati.
6. TDD: `tests/infra/test_acr_oauth_data_plane_login.py` usa fake `subprocess.run` per Azure/Docker e un HTTPS opener finto. RED con script e integrazione assenti, poi GREEN su host allowlist, tenant, audience ACR, token stdin, redirect/CLI/HTTP/json/token fail-closed, nessuna perdita di secret. CI 7/7 sullo stesso SHA `main` per chiudere **la sola #73**.

## Confini non risolti / prove live

- `az acr manifest show-metadata` e `az acr repository update/show` nel resolver di digest e nel lock continuano a usare comandi Azure CLI con requisiti possibili di **control-plane** non risolti dal nuovo Docker login. **#72 resta aperta** finché l'owner non avrà verificato se quelle operazioni siano effettuabili dal principal con `AcrPush` o finché non sarà progettato un accesso sicuro via API data-plane e testato con fake più Azure reale. Non conferire `Contributor`/`Owner`/admin all'identità build come workaround.
- Il token ACR refresh può rimanere in cache Docker durante il job: l'isolamento in un unico runner non è forte e #70 rimane aperta per lo split in job separati/runner, protezioni del token broker OIDC, revoche e review delle federated credentials. La pipeline può fallire prima dell'apply se i ruoli sono insufficienti; è il comportamento corretto.
- La CI offline non ha chiamato Microsoft Entra, registry HTTPS o Docker reali: il fake verifica il protocollo, **non l'effettiva emissione del refresh token o i permessi push/lock**. Non sono stati eseguiti `terraform apply`, operazioni Azure live, creazione di FIC/ruoli, accesso ai secret Key Vault o promozioni di traffico. #65/#5/#6/#49 restano aperte.
